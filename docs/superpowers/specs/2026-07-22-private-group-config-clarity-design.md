# 私密分组配置清晰化设计

## 目标

在现有“系统设置 -> 分组/倍率”界面内，把分组定价、普通用户可见性、特殊授权和渠道路由能力之间的关系表达清楚，同时修复已授权用户通过控制台访问令牌读取不到私密分组价格的问题。

本设计不创建独立分组管理页面，不改变 `下游` 作为独立渠道分组的语义，不修改本地实验 UI，也不涉及直连域名部署。直连域名将作为独立基础设施变更处理。

## 已确认现状

- `GroupRatio` 定义分组倍率。
- `UserUsableGroups` 决定哪些分组默认对普通用户可见和可选。
- `group_ratio_setting.group_special_usable_group` 可以为指定用户组增加或移除可用分组。
- `channels.group` 和 `abilities.group` 决定分组实际具备哪些渠道和模型。
- 私密分组不在 `UserUsableGroups` 中，因此匿名用户和未授权普通用户不应在价格页、令牌分组选择器或用户模型列表中看到它。
- 生产端 `下游` 分组已有一个启用渠道和四条启用能力，标准 `/v1/models` 请求可以返回 `gpt-5.5`、`gpt-5.6-luna`、`gpt-5.6-sol`、`gpt-5.6-terra`。
- 当前 `TryUserAuth` 只识别旧 Session。携带有效控制台访问令牌请求 `/api/pricing` 时仍被当作匿名用户，私密分组及其倍率会被过滤。

## 方案比较

### 方案 A：只修改说明文字

保留现有表格和字段，仅补充帮助文案。

优点是改动最小。缺点是管理员仍然无法直接看到一个分组是否公开、是否已授权、是否具备可用渠道和模型，配置错误只能在调用失败后发现。

### 方案 B：增强现有配置表并增加只读覆盖状态（采用）

继续使用现有分组配置页面，在原表格中明确显示公开/私密状态和已保存的路由覆盖情况；特殊授权仍在现有规则编辑器中配置。后端提供管理员专用的只读分组目录数据，并修复控制台令牌的可选鉴权。

该方案不增加新页面，能在保存前后给出足够明确的配置反馈，且不会把渠道编辑、用户授权和分组定价混成一个大型表单。

### 方案 C：在分组表中直接编辑渠道和用户

把渠道分配、用户授权、倍率和可见性全部放进一个界面。

该方案看似集中，但会复制渠道管理和用户管理能力，增加权限边界与保存事务复杂度，也容易引入跨模块状态不同步，因此不采用。

## 管理端界面设计

现有 `GroupPricingTable` 保持为页面主入口，不创建新页面。表格调整为以下信息：

| 列 | 含义 |
| --- | --- |
| 分组名称 | 稳定的路由和计费标识，不改变现有保存格式 |
| 倍率 | 当前 `GroupRatio` 值 |
| 可见性 | 显示“公开”或“私密”状态；公开表示存在于 `UserUsableGroups` |
| 路由覆盖 | 显示启用渠道数和启用模型数 |
| 描述 | 仅公开分组编辑普通用户描述；私密分组显示固定的授权提示，不新增描述存储 |
| 操作 | 保留删除等现有操作 |

现有“用户可选”复选框改为含义明确的公开/私密控制：

- 打开：公开分组，普通用户可在令牌创建下拉框和公开价格数据中看到。
- 关闭：私密分组，普通用户不可见；只有用户本身属于该分组，或通过特殊可用规则明确授权后才能看到和选择。
- 新建分组默认保持当前行为，但界面必须在切换为私密时显示明确状态，不依赖管理员理解底层 JSON。
- 私密分组不把说明写入 `UserUsableGroups`；描述列固定显示“仅通过用户组授权”，避免为界面文案新增配置字段。

每一行增加路由覆盖状态：

- 有启用渠道和模型：显示具体数量。
- 倍率已配置但没有启用能力：显示阻断级提示“无可用模型，调用将失败”。
- 新增但尚未保存的分组：显示“保存后检查路由覆盖”，不伪造实时数据库状态。

特殊可用规则编辑器继续留在当前页面，文案改为明确的“用户组授权”：

- 左侧用户组是被授权者的用户分组。
- 目标分组是要开放的私密分组。
- `+:` 只改变可见性和可选权限，不会创建渠道、复制模型或改变分组倍率。
- 目标分组没有路由覆盖时，在规则行显示警告。

## 管理员只读分组目录

在现有管理员保护的 `/api/group` 路由组下新增只读目录接口，不改变现有 `GET /api/group/` 的字符串数组契约。

建议接口：

```text
GET /api/group/catalog
```

每个分组返回：

```json
{
  "name": "下游",
  "ratio": 0.028,
  "public": false,
  "description": "",
  "active_channel_count": 1,
  "active_model_count": 4,
  "active_models": [
    "gpt-5.5",
    "gpt-5.6-luna",
    "gpt-5.6-sol",
    "gpt-5.6-terra"
  ]
}
```

接口只对管理员开放。数据由当前内存倍率配置和数据库启用能力组合生成，不修改任何渠道、用户或分组设置。数据库查询使用 GORM，并兼容 SQLite、MySQL 和 PostgreSQL。

## 用户可见性与授权

权限判断继续以后端为准，前端仅展示后端已过滤的数据：

- 匿名用户：只能获得 `UserUsableGroups` 中的公开分组及对应模型。
- 未授权普通用户：行为与匿名用户相同，不得仅凭分组名称或 URL 查询私密分组。
- 已授权用户：可以获得公开分组和特殊规则授予的私密分组。
- 用户本身属于私密分组：保留现有“用户自身分组可用”行为。
- 管理员：可以通过管理员目录看到全部分组及路由覆盖状态。

价格页和令牌分组选择器继续使用 `/api/pricing` 与 `/api/user/self/groups` 返回的数据，不在浏览器中拼接或猜测私密分组。

## 控制台令牌鉴权修复

从父项目的无状态鉴权变更中移植最小必要逻辑，不整体合并认证重构：

- `TryUserAuth` 先识别现有 Session。
- 没有 Session 但存在有效控制台访问令牌时，加载对应用户并写入 `id`、`group`、`user_group`、角色和状态上下文。
- 无凭证请求保持匿名访问。
- 提供了凭证但凭证无效时返回明确的未授权响应，不能静默降级为匿名用户。
- 普通 relay API Key 仍通过 `/v1/models` 和 relay 路由鉴权；本变更不把 relay API Key 混同为控制台访问令牌。

修复后，已授权用户通过控制台访问令牌请求 `/api/pricing` 时能够获得私密分组倍率和模型；未授权用户仍然被过滤。

## 错误与一致性处理

- 分组名称为空或重复时阻止保存。
- 私密分组没有路由覆盖时允许保存倍率，但必须显示调用失败警告，避免把配置界面变成隐式渠道编辑器。
- 特殊授权指向不存在的倍率分组时显示错误。
- 特殊授权指向没有启用能力的分组时显示警告。
- 删除分组前，如果仍存在特殊授权规则或启用渠道能力，显示依赖提示；本轮不自动删除渠道或授权规则。
- 所有安全过滤都由后端执行，UI 隐藏不作为权限控制手段。

## 测试设计

后端测试覆盖以下契约：

- 匿名价格请求不返回私密分组、私密倍率或仅属于私密分组的模型。
- 未授权用户不返回私密分组。
- 特殊规则授权用户能够返回私密分组、倍率和模型。
- 控制台访问令牌能够被 `TryUserAuth` 识别并写入正确用户组。
- 无效控制台访问令牌不会降级为匿名请求。
- 管理员目录正确计算公开/私密状态、启用渠道数、去重模型数和模型列表。
- 管理员目录接口拒绝普通用户访问。
- 属于私密分组的 relay API Key 调用 `/v1/models` 时只返回该分组实际启用的模型。

前端测试与验证覆盖：

- 公开和私密状态能从 `GroupRatio` 与 `UserUsableGroups` 稳定往返序列化。
- 无路由覆盖、未保存和正常覆盖三种状态显示正确。
- 特殊授权编辑器明确区分授权和路由能力。
- 所有新增界面文本使用 `t(...)`，并通过脚本写入 `en`、`zh`、`fr`、`ja`、`ru`、`vi` 六个语言文件。
- 运行前端格式检查、i18n 同步、相关 Go 测试和生产构建。

## 部署边界

- 只修改生产仓库中的后端鉴权、管理员分组目录、现有分组设置组件和必要翻译。
- 不修改本地实验 UI。
- 不更改现有 `下游` 渠道、模型、倍率或用户授权数据。
- 数据库无需破坏性迁移。
- 生产部署前备份数据库和 Compose 配置；只重建 `newapi` 服务并等待健康检查。
