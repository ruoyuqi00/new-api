# 敏感输入原文审计与定期清理设计

## 背景

YuAPI 当前会在启用敏感输入检查的分组中，于请求转发前检查 `TokenCountMeta.CombineText`。命中本地敏感词后，请求被阻断并按输入 Token 成本扣费，但消费日志只记录 `Sensitive input blocked`，管理员无法判断具体命中了什么内容。

本设计为部署后的新拦截记录保存受检原文与命中词，并提供管理员查看和 7 天自动清理能力。历史日志没有保存原文，无法补录。

## 目标

- 管理员可在消费日志详情中查看本地敏感词拦截时的受检原文和命中词。
- 原文最多保存 64 KiB，且不能因截断产生非法 UTF-8。
- 普通用户和 Token 自助日志接口不得返回原文或命中词。
- 原文和命中词保留 7 天，之后自动清除；管理员可手动立即执行同一保留策略。
- 清理后保留用户、模型、时间、Token 数、扣费金额、倍率和扣费结果等账务审计信息。
- 不改变敏感词匹配、分组开关、扣费、拦截响应和重试行为。

## 非目标

- 不保存请求头、API Key、附件、图片、音频或原始 HTTP 请求体。
- 不恢复部署前历史日志的原文。
- 不改变 OpenAI Moderation 或上游违规扣费记录的内容策略；本期只处理 `local_sensitive_word`。
- 不新增通用的请求正文日志功能。

## 方案选择

使用现有 `logs.content` 保存受检原文，使用 `logs.other` 保存小型结构化审计元数据。生产 MySQL 中两个字段均为 `LONGTEXT`，无需数据库迁移；SQLite 和 PostgreSQL 继续使用现有字符串字段。

不把大段原文放入 `other`，避免每次解析日志元数据时处理大型 JSON。也不新增独立加密表，以免引入迁移、密钥管理和额外查询链路。原文在数据库中为明文，应用接口通过后端权限过滤保护；数据库管理员仍可直接读取。

## 数据流

1. `controller.Relay` 使用当前逻辑构建 `meta.CombineText`。
2. `service.CheckSensitiveText` 返回是否命中及命中词列表。
3. 命中后继续完成 Token 估算和输入费用计算，保持现有单次扣费流程。
4. 调用本地违规扣费记录函数时，同时传入：
   - 实际受检文本 `meta.CombineText`
   - 命中词列表
5. 日志记录前按 UTF-8 边界截取最多 65,536 字节。
6. 管理员日志接口返回保存内容；普通用户日志格式化阶段执行服务端脱敏。
7. 清理任务到期后将正文恢复为通用提示并移除命中词。

## 日志格式

本地敏感词拦截记录继续使用消费日志类型，字段如下：

- `content`: 截取后的受检原文；清理后为 `Sensitive input blocked`。
- `other.violation_fee_reason`: `local_sensitive_word`。
- `other.sensitive_words`: 去重后的命中词字符串数组。
- `other.sensitive_input_original_bytes`: 截取前字节数。
- `other.sensitive_input_truncated`: 是否超过 64 KiB。
- `other.sensitive_input_purged`: 清理后为 `true`。
- `other.sensitive_input_purged_at`: 清理时间戳。

现有扣费字段保持不变。命中词不写入普通应用日志或错误响应。

## 权限与脱敏

管理员的全量日志接口可返回原文和命中词。所有普通用户路径，包括用户日志列表和按 Token 查询日志，必须在后端执行以下处理：

- 当 `violation_fee_reason == local_sensitive_word` 时，将 `content` 替换为 `Sensitive input blocked`。
- 从 `other` 删除 `sensitive_words`。
- 不依赖前端隐藏来实现权限控制。

前端只有在 `isAdmin` 且日志属于本地敏感词违规时展示原文审计区。React 以普通文本节点渲染原文，不使用 HTML 注入。

## 管理后台

消费日志详情中的违规扣费区域增加：

- `Matched sensitive words`: 展示命中词。
- `Blocked input`: 展示受检原文，使用限高滚动容器并保留换行，提供复制按钮。
- `Content truncated`: 当原文超过 64 KiB 时显示截断提示和原始字节数。
- `Content purged`: 到期清理后显示已清理状态，不再展示原文和命中词。

敏感词设置附近增加：

- 管理员可配置的原文保留天数，默认及生产值为 7，允许范围 1 到 365 天。
- `Run cleanup now` 按钮，执行当前保留策略，只清理已超过保留期的记录。
- 清理操作需要确认，并展示清理记录数。

所有新增文案覆盖 `en`、`zh`、`fr`、`ja`、`ru`、`vi`。

## 定期清理

复用现有系统任务框架注册敏感输入清理任务：

- 每天自动运行一次，按服务器时区计算 7 天截止时间。
- 管理员可手动创建同类型任务立即执行。
- 以小批次读取超过截止时间的本地敏感词消费日志，默认每批 200 条。
- 在 Go 中解析 `other`，只处理仍含原文或命中词且尚未清理的记录。
- 每条更新 `content` 和清理后的 `other`；任务可重复执行且结果幂等。
- 任务进度记录扫描数、清理数和失败数，不记录原文或命中词。

查询使用 GORM 和可移植的 `LIKE`/时间条件，不依赖 MySQL JSON 函数，确保 SQLite、MySQL 和 PostgreSQL 可用。清理任务不得长事务锁住整个日志表。

## 错误处理

- 原文截取或元数据整理失败时，仍然执行原有拦截和扣费，最多回退为通用日志内容。
- 日志写入失败沿用现有日志失败处理，不得改变客户端拦截结果。
- 自动清理单批失败时记录不含敏感内容的系统错误并结束任务，下一次运行可继续。
- 手动清理失败时在系统任务中显示失败原因，不删除账务字段。

## 测试

后端测试保护以下契约：

- 受检原文和命中词写入本地敏感词违规日志。
- 超过 64 KiB 的多字节文本按合法 UTF-8 边界截断并标记。
- 普通用户日志和按 Token 日志不返回原文或命中词，管理员日志保留。
- 清理任务只清除超过 7 天的本地敏感词原文，不删除账务字段，不影响其他日志。
- 清理任务重复运行保持幂等。
- 新增参数不改变违规输入只扣费一次的现有不变量。

前端测试保护以下行为：

- 管理员详情显示命中词、原文和截断/清理状态。
- 普通用户详情不渲染管理员审计区。
- 长文本在固定区域滚动，不撑开对话框。

## 部署与回滚

- 该方案不包含数据库结构迁移。
- 构建新生产镜像，先启动候选容器并验证健康检查、日志接口权限和清理任务，再无缝替换正式容器。
- 回滚只需恢复上一镜像；新字段位于 JSON 元数据中，旧版本会忽略。
- 部署后使用测试账号发起一条明确命中的短输入，验证拦截、单次扣费、管理员可见、普通用户脱敏，然后删除测试产生的敏感原文。

## 验收标准

- 新违规记录的管理员详情可以准确看到受检原文和命中词。
- 普通用户 API 响应中不存在原文和命中词。
- 64 KiB 上限和 UTF-8 完整性测试通过。
- 7 天自动清理和手动立即执行均只清除到期原文与命中词。
- 清理前后扣费金额和账务审计字段保持一致。
- 生产容器健康且重启次数没有异常增加。
