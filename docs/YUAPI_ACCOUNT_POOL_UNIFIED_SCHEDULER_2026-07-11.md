# YuAPI 账号池统一调度（2026-07-11）

## 用户边界

用户仍然只选择分组和模型。渠道、账号池和具体供应商账号均为管理员侧资源，不进入用户请求协议，也不向普通用户暴露。

```text
用户分组 + 模型 + 请求协议
  -> 渠道优先级 / 权重 / 并发 / 冷却
  -> 账号池优先级 / 权重 / 分组
  -> 账号优先级 / 权重 / 过期 / 并发 / 冷却
  -> 最终上游凭据
```

传统渠道没有账号池绑定时继续使用 `channels.key`，因此升级不要求一次性迁移现有渠道。渠道绑定账号池后，运行时忽略渠道内置 Key，改用账号池选出的凭据。

## 数据模型

- `account_pools`：供应商、用户分组、池优先级、池权重和启停状态。
- `provider_accounts`：凭据类型、凭据、账号优先级、账号权重、并发、冷却和过期时间。
- `channel_account_pool_bindings`：渠道与账号池的多对多绑定。

三张表均由 GORM `AutoMigrate` 创建，使用普通字段和关联查询，兼容 SQLite、MySQL 和 PostgreSQL。

## 调度语义

1. 现有渠道调度先确定可服务当前分组、模型和协议的渠道。
2. 渠道没有启用的账号池绑定时走原有单 Key / Multi-Key 路径。
3. 有绑定时，只选择启用且包含当前用户分组的账号池。
4. 先使用最高账号池优先级；同级按权重随机。高优先级池不可用时降到下一优先级。
5. 池内先使用最高账号优先级；同级按权重随机。账号过期、禁用、冷却或并发已满时先过滤。
6. Redis 可用时账号并发租约跨实例共享；否则使用进程内计数。租约 TTL 为 6 小时。
7. 429、529、适用的 5xx、409 和 425 可触发账号级冷却；明确的认证错误会禁用具体账号，而不是整个渠道。
8. 普通消费日志的管理员信息记录 `account_pool_id`、`provider_account_id` 和账号名称，普通用户不可见。

账号池快照随渠道缓存一起周期刷新，管理端增删改后立即刷新。关闭内存缓存时使用数据库路径，行为保持一致。

## 管理端

侧边栏新增“账号池”，与“渠道”分开：

- 创建和编辑账号池；
- 设置账号池所属用户分组、优先级和权重；
- 绑定一个或多个渠道；
- 单个添加或按行批量导入 API Key、OAuth JSON、Cookie 和自定义凭据；
- 设置账号优先级、权重、并发、冷却和启停状态；
- 删除账号或完整账号池。

凭据不在列表和详情 API 中返回。编辑已有账号时留空凭据表示保留原值。单独读取完整凭据的接口要求超级管理员、安全验证和关键操作限流。

## 当前边界

- 账号凭据会复用绑定渠道的现有协议适配器；只有适配器能够把该凭据当作渠道 Key 解析时才能直接运行。
- Codex OAuth 自动刷新目前仍以传统 Codex 渠道凭据为入口。账号池内 OAuth 的独立刷新任务需要按供应商逐个迁移。
- Kiro、Windsurf 和其他 Sub2API 专属适配器仍需移植其协议模块，不能仅靠导入凭据获得支持。
- 本次没有读取或导入旧 Sub2API 生产账号。正式导入前应先生成不含密钥的只读清单并按平台逐批回归。
