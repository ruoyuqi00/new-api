# YuAPI 调度、计费与上游更新审计（2026-07-11）

## 1. 渠道选择规则

一次请求先确定用户可用分组和模型，再过滤禁用渠道、请求协议不匹配的高级自定义渠道、冷却中的渠道、已达到渠道并发上限的渠道，以及本次选择中已经跳过的渠道。

### 优先级

- `priority` 数值越大，优先级越高。
- 首次选择使用当前可用候选中的最高优先级。
- 上游失败并允许重试时，`retry=1` 使用下一档优先级，之后继续向下。
- 重试次数超过优先级档数时，继续使用最低优先级档。
- 如果高优先级渠道已满或处于冷却期，它会在选择前被过滤，因此本次请求可以直接降到下一档可用优先级。

示例：渠道 A/B 为 `priority=120`，渠道 C 为 `priority=80`。首次请求只在 A/B 中选择；允许重试后才进入 C。若 A/B 都达到并发上限，首次请求可直接选择 C。

### 权重

- 权重只在同一优先级内生效，不会跨优先级比较。
- 同层存在正权重时，按权重占比随机选择。例如 A/B 的 `weight=70/30`，长期流量约为 70%/30%。
- 同层全部为 `weight=0` 时，按等权选择，避免未配置权重的渠道池不可用。
- 同层同时存在正权重与零权重时，零权重渠道不接收正常随机流量；可将其作为手动启用前的占位配置。

本次修复前，关闭内存缓存时会给每个渠道隐式增加 `10` 权重，而开启缓存时使用真实权重，导致相同配置在两种运行模式下分流不同。现在数据库路径与缓存路径统一使用以上规则。

### 自动分组和亲和性

- 普通令牌只在令牌指定分组内调度。
- `auto` 分组按管理员配置的自动分组顺序查找；启用跨组重试后，会在当前组内按重试规则消耗优先级，再进入下一组。
- 渠道亲和性可以优先复用先前成功的渠道，但禁用、模型不匹配、协议不匹配、冷却或并发已满时不会强行复用。
- `RetryTimes` 是失败后的最大重试次数；总尝试次数通常为 `RetryTimes + 1`，是否重试还受状态码、错误类型和“禁止重试”标记控制。

## 2. 两套并发限制

### 用户并发

- 默认限制每个已认证用户同时进行的模型请求数，可由用户/令牌分组配置覆盖。
- Redis 可用时，本次修改后计数在多应用实例间共享；Redis 异常时记录错误并回退到进程内计数，以保证模型 API 不因 Redis 短暂故障全部中断。
- 请求结束（包括流式响应结束）后释放计数；租约设置 6 小时 TTL，降低进程异常退出造成永久占位的风险。

### 渠道池并发

- 每个渠道可单独设置并发上限；`<=0` 表示不限制。
- 获取租约是原子的，Redis 可用时跨实例共享，否则使用进程内计数。
- 上游返回 429、529、部分 5xx、409 或 425 时，可按渠道配置进入冷却。
- 用户并发限制保护站点容量，渠道并发限制保护具体上游账号，两者独立且会同时生效。

## 3. 计费审计结论

- 已有任务差额结算、异步任务 quota 持久化、图片数量和视频时长边界、任务/文本结算饱和保护与审计字段。
- 本次补上预扣费严格范围检查：固定价格、倍率价格、按次价格和分层表达式的预扣额度超出 int32 quota 范围时直接拒绝，不再把饱和值或负数交给扣费会话。
- 分层表达式仍以 `pkg/billingexpr/expr.md` 为唯一语义依据；客户端未传 `max_tokens` 时使用现有默认估算，最终按真实用量结算。

## 4. 上游更新处理

已选择性移植：

- `70ea899e3`：将失效的 GORM v1 `FOR UPDATE` 写法替换为 GORM v2 行锁，并为 SQLite 保留兼容路径；同时增加兑换码并发只入账一次的原子更新。
- `56dbaab1d` 的 Secure Session Cookie 核心能力：新增 opt-in 环境变量和 HTTPS 入口校验，未引入其无关的中间件改名。
- `621927f71` / `d9595831b` 的预扣额度越界拒绝逻辑按当前分支计费结构手工移植，保留 YuAPI 已有图片和任务计费适配。

暂不直接整体合并：

- `269e4ff39` 改动图片流式协议和图片数量计费，和当前 YuAPI 的 GPT Image 2、UAG 及断连处理重叠，需要按渠道做真实流式回归后再移植。
- `df087b022` 增加 DNS/重定向阶段 SSRF 防护。当前已有 URL 级 SSRF 校验，但还缺少完整的连接阶段防护；这是下一批安全更新的高优先级候选。
- 上游近期默认前端设计系统提交不整体合并，避免覆盖 YuCore 品牌和工作台实现。

## 5. 建议配置例

稳定主渠道 A/B：`priority=120`，`weight=70/30`，配置各自真实并发上限。备用渠道 C：`priority=80`，`weight=100`，配置 429/5xx 冷却。灾备渠道 D：`priority=20`，`weight=100`。这样正常流量只进入 A/B，容量耗尽或失败重试时依次降级到 C、D。
